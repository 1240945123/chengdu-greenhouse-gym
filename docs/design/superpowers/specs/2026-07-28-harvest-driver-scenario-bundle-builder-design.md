# Harvest Driver Scenario Bundle Builder Design

## Goal

Generate production-ready harvest uncertainty driver scenarios from complete,
audited GreenLight state trajectories instead of hand-edited driver CSVs or
arbitrary numeric perturbations.

## Manifest

A YAML manifest declares:

- timezone and maximum driver interval;
- the accepted point-driver CSV used by held-out prediction;
- one shared test-season identity and model-evidence block;
- at least two scenarios, each with a unique `driver_scenario_id`, an allowed
  `driver_uncertainty_source`, and a GreenLight state-trajectory path.

The shared season block contains `season_id`, greenhouse ID/code,
`planting_code`, initial fruit maturity fraction, `season_complete`,
`driver_model_status`, and air-temperature source. Production scenario bundles
require complete seasons and `accepted_target_crop_model`.

## Build Flow

The command loads confirmed periods from the field workbook's
`HarvestProtocol`. For every scenario trajectory it invokes the existing
state-to-driver builder, preserving fruit-state mass accounting and deriving
`pick` only from the protocol. It adds the scenario ID/source columns, combines
all scenarios, and calls `validate_uncertainty_driver_scenarios` against the
point driver.

The final validator requires identical season/timestamp keys, fixed fields,
target identity, step widths, and protocol picks. Only physical drivers and
initial fruit state may differ. Therefore the output can be passed directly to
`--uncertainty-driver-scenarios` without a second manual transformation.

## Outputs

- UTF-8 CSV containing canonical scenario driver rows;
- JSON audit containing resolved source paths, scenario IDs/sources, per-
  scenario state-to-driver audits, protocol provenance, and final alignment
  audit.

The builder writes outputs only after all scenarios pass. It never downgrades
diagnostic/incomplete inputs into accepted evidence.

## Failure Rules

Reject fewer than two scenarios, duplicate IDs, unsupported uncertainty
sources, missing files/fields, incomplete or unaccepted shared season status,
missing/provisional protocol coverage, nonzero mass-accounting errors beyond
the existing driver tolerance, and any mismatch against point-driver keys or
fixed fields.

## Verification

Tests build two synthetic trajectories with different physical fruit changes
and prove aligned output, source metadata, protocol-derived picks, and audit
reconciliation. Negative tests cover unknown sources, mismatched timestamps,
and diagnostic/incomplete status. The full suite must pass.

## Current Target Status

No Pidu production scenario bundle is generated by this feature because the
current target crop trajectory is diagnostic and the season is incomplete.
Real scenario generation begins only after accepted GreenLight climate/crop
ensembles exist.
